Chess notation, parsed

Everything below is driven by a single grammar for PGN — the notation chess games have been recorded in since 1994. The board is not the point. The point is what it takes to teach a parser a new language, and how little that turns out to be.

A grammar is a table, not a program

This is the part worth carrying away. A tabnas grammar is data: a table saying, for each rule, which token opens which alternative and what to do about it. Nobody generates a parser, and nobody writes a recursive-descent function by hand.

Here is the whole of the rule that reads one element of a game — a move, a move number, a glyph, a comment, or a nested variation: 

# A movetext element (PGN spec 8.2).
rule: element: open: [
  { s: '#SAN' a: '@move'          g: 'elem,move' }
  { s: '#MVN' a: '@number'        g: 'elem,number' }
  { s: '#NAG' a: '@nag'           g: 'elem,nag' }
  { s: '#CMT' a: '@brace-comment' g: 'elem,comment' }
  { s: '#RMK' a: '@line-comment'  g: 'elem,comment' }
  { s: '#OP'  p: rav b: 1 u: { rav: true } g: 'elem,rav' }
]
rule: element: close: [
  { s: '#ELEM' r: element b: 1 g: 'elem,next' }   # another element
  { s: '#EEND' b: 1 g: 'elem,end' }               # hand back up
]

s is the token that selects the alternative, a an action, p a rule to descend into, r one to become, b how many tokens to give back. That is most of the vocabulary. Because it is data, you can print it, diff it, generate it — or hand it to an agent to write.

One table, two languages

The grammar above lives in a single file. The build embeds the same compiled JSON into the TypeScript package and the Go module, so the two implementations cannot drift apart in the one place where drift would be hardest to spot.

TypeScript

import { parseGame } from '@tabnas/chess'

const game = parseGame('1. e4 e5 *')
game.moves[0].san    // 'e4'
game.moves[0].piece  // 'P'

Go

import chess "github.com/tabnas/chess/go"

db, _ := chess.Parse("1. e4 e5 *")
db[0].Moves[0].San    // "e4"
db[0].Moves[0].Piece  // "P"

They are held to it. A shared fixture set of tab-separated cases is run by both suites and compared against the same expected JSON — 351 assertions on the TypeScript side, the identical corpus on the Go side. A change that moves one runtime and not the other fails before it lands.

What comes back is plain data

No classes, no cycles, nothing to unwrap. Every field is something the notation actually said — and nothing that it did not. This parser has no board, so it will not tell you which knight played Nf3; it records the piece and the destination, because that is what was written. 

parseGame('1. e4 {Best by test.} e5 (1... c5) 1-0')

{
  tags: {},
  moves: [
    { san: 'e4', piece: 'P', to: 'e4', number: 1, side: 'w',
      comments: [ { kind: 'brace', text: 'Best by test.' } ] },
    { san: 'e5', piece: 'P', to: 'e5', number: 1, side: 'b',
      variations: [ { moves: [ { san: 'c5', piece: 'P', to: 'c5', … } ] } ] }
  ],
  result: '1-0'
}

Try it — the notation is editable

This board re-parses as you type. A half-typed game is the normal state of an editor rather than a failure, so the position holds while you are mid-move and the parser says what is wrong underneath.

1. d4 d5 2. c4 {The Queen's Gambit.} e6 3. Nc3 Nf6 *

Delete a bracket and watch the message change. Those messages are not the engine's — see below.

Error messages belong to the grammar

An engine that knows nothing about chess can only report that a character matched no active rule. A grammar can do better, because it knows what the language is made of. Tabnas lets a grammar replace the text for any error code, with a longer hint behind it: 

error: {
  unexpected:           'not chess notation: {src}',
  unterminated_comment: 'this comment is never closed',
  unprintable:          'a tag value cannot contain a line break',
}

The component adds the one thing a grammar cannot know from the inside — where you are looking — and the source, so it can name the bracket you left open rather than the character the lexer happened to stop on:

1. e4 zz

1. e4 zz

1. e4 (e5

1. e4 (e5

Where the parser stops

@tabnas/chess reads notation. It has no board, so it accepts any well-formed move: 1. Qh8 parses happily and 1. e9 does not, because the first is a legal move to write and the second is not a move at all.

Showing a game needs the missing half, so this component carries a small legal move generator that resolves each parsed move against the running position — tested with perft against published node counts. A move that is good notation but not legal here stops its line and says so:

1. e4 e5 2. Nf3 Nc6 3. Qxh8 {No queen can reach h8 here.} 1-0

Commentary, in a panel of its own

Comments are kept, not discarded — the standard has two forms and both survive into the model. Here the prose is given a box that follows the position, which reads better than threading it through the moves. The notes are original, written for this page.

Clocks, evaluations, and markup the standard never defined

The [%clk] markup lichess and chess.com emit is not in the 1994 standard — it comes from a 2001 supplement, which also asks that commands be stripped before display. They are, and the ones that mean something to a reader become a chip.

[Event "Rated Blitz game"] [TimeControl "180+0"] 1. e4 { [%clk 0:03:00] [%eval 0.17] } e5 { [%clk 0:02:58] } 2. Nf3 { [%clk 0:02:57] [%eval 0.21] Book. } Nc6 { [%clk 0:02:55] } 3. Bb5 { [%clk 0:02:52] } a6 { [%clk 0:02:49] } 1/2-1/2

A study, from a set position

A FEN tag says where play starts, so the move numbers and the side to move come from the game rather than from move one.

[SetUp "1"] [FEN "8/6P1/8/8/8/1k6/8/K7 w - - 0 51"] 51. g8=Q+ {The pawn queens with check along the long diagonal.} Kb4 52. Qb8+ Ka4 53. Qb2 {The queen cuts the king off; the white king walks up.} 1-0

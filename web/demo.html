<chess-view> a chessboard for any page

One script tag. Paste a game in, get a board you can step through. No dependencies, no configuration, no second request.

Put a chess game on a page

The game is the markup. Write the notation between the tags and that is the whole integration — the board, the move list, the controls and the parser arrive in one file.

Install

From a CDN, pinned — the same URL without a version follows the latest release, which is convenient right up until it is not: 

<script src="https://cdn.jsdelivr.net/npm/@tabnas/chess-view@0.1.3"></script>

<!-- or as a module -->
<script type="module"
  src="https://cdn.jsdelivr.net/npm/@tabnas/chess-view@0.1.3/dist/chess-view.mjs"></script>

Or from npm, where it has no dependencies at all — the parser is bundled in, and so are the TypeScript declarations: 

npm install @tabnas/chess-view

// importing registers the element
import '@tabnas/chess-view'

Every release ships the integrity hashes of the files it published, at dist/sri.json, so a pinned <script> can carry an integrity attribute. Importing on a server is safe: nothing touches the DOM until the element registers, and registration is skipped where there is no custom element registry.

The options

Ten attributes, and that is the whole surface. The last four are subtractive — each takes a part of the UI away and the rest closes up around it.

AttributeValuesWhat it does
orientationwhite, blackWhich side is at the bottom.
plya numberWhich move to open at. 0 is the starting position.
gamea numberWhich game of a multi-game database to show.
themeauto, darkauto follows the reader's system setting.
sourcehidden, view, editShow the notation itself, read-only or editable.
commentaryinline, panel, hiddenWhere the annotator's prose goes.
controlsvisible, hiddenThe navigation buttons.
notationvisible, hiddenThe whole side panel.
tagsvisible, hiddenThe players-and-event header.
coordinatesvisible, hiddenThe file and rank labels.

source="edit" — let the reader type

The board re-parses as you type. A half-typed game is the normal state of an editor rather than a failure, so the position holds while you are mid-move and the message underneath says what is wrong. Try deleting a bracket.

1. d4 d5 2. c4 {The Queen's Gambit.} e6 3. Nc3 Nf6 *

commentary="panel" — prose in a box of its own

Comments are kept, not discarded, and both of the standard's two forms survive. Inline they read as an annotated game does on paper; in a panel they follow the position, which is better when there is a lot of them. These notes are original, written for this page.

theme="dark", and starting from a position

A FEN tag says where play starts, so the move numbers and the side to move come from the game rather than from move one. Leave theme off and the board follows the reader's system setting.

[SetUp "1"] [FEN "8/6P1/8/8/8/1k6/8/K7 w - - 0 51"] 51. g8=Q+ {The pawn queens with check along the long diagonal.} Kb4 52. Qb8+ Ka4 53. Qb2 {The queen cuts the king off; the white king walks up.} 1-0

Everything off, plus ply — just a diagram

With the notation, the controls and the coordinates all hidden, what is left is a static diagram opened at whichever move you name. The arrow keys still work, because hiding the buttons hides the buttons and nothing else. 

<chess-view notation="hidden" controls="hidden" coordinates="hidden" ply="33">
  1. e4 e5 2. Nf3 d6 …
</chess-view>

Controls

Buttons for start, previous, next, end and flip — and the same from the keyboard whenever the component has focus: ← → Home End f. Clicking any move in the notation jumps straight to it.

From JavaScript

Two events, both bubbling, so a listener on document works: 

document.addEventListener('chess-move', (e) => {
  e.detail.ply        // how far in, 0 is the start
  e.detail.move?.san  // 'Nf3', or undefined at the start
})

// only when source="edit"
document.addEventListener('chess-source', (e) => {
  if (e.detail.ok) save(e.detail.source)
  else console.log(e.detail.error)
})

And on the element itself:

el.moveThe move currently shown, or undefined.
el.plyHow far into the current line the view is.
el.sourceThe notation being shown. Settable.
el.goto(n)Show the nth move of the current line.
el.load()Re-read the source. Called automatically on change.

TypeScript users get the declarations in the package, wired into the editor's own model of HTML: querySelector('chess-view') is a ChessViewElement without a cast, and e.detail above is typed.

When the notation is wrong

A parse error is written for someone holding a PGN file, not for someone debugging a grammar — with the whole word that failed, where it is, and the bracket you left open when that is the real problem.

What it will not do

It reads notation, and it plays that notation onto a board. It is not a chess engine: it will not evaluate, suggest, or let you drag pieces, and it does not adjudicate draws by repetition or the fifty-move rule.

A move that is well-formed notation but not legal in the position stops its line and says so — a different failure from a syntax error, and reported as one:

1. e4 e5 2. Nf3 Nc6 3. Qxh8 {No queen can reach h8 here.} 1-0

Markup the standard never defined

The [%clk] markup lichess and chess.com emit is not in the 1994 standard — it comes from a 2001 supplement, which also asks that commands be stripped before display. They are, and the ones that mean something to a reader become a chip instead.

[Event "Rated Blitz game"] [TimeControl "180+0"] 1. e4 { [%clk 0:03:00] [%eval 0.17] } e5 { [%clk 0:02:58] } 2. Nf3 { [%clk 0:02:57] [%eval 0.21] Book. } Nc6 { [%clk 0:02:55] } 3. Bb5 { [%clk 0:02:52] } a6 { [%clk 0:02:49] } 1/2-1/2

What is underneath: tabnas

If you only wanted a board, you have it — this is the part for anyone wondering how the notation gets read, or who needs to teach a parser a different language tomorrow.

Everything above is driven by a grammar for PGN, running on tabnas. The interesting claim is that the grammar is data: a table saying, for each rule, which token opens which alternative and what to do about it. Nobody generates a parser, and nobody writes a recursive-descent function by hand.

Here is the whole of the rule that reads one element of a game — a move, a move number, a glyph, a comment, or a nested variation: 

# A movetext element (PGN spec 8.2).
rule: element: open: [
  { s: '#SAN' a: '@move'          g: 'elem,move' }
  { s: '#MVN' a: '@number'        g: 'elem,number' }
  { s: '#NAG' a: '@nag'           g: 'elem,nag' }
  { s: '#CMT' a: '@brace-comment' g: 'elem,comment' }
  { s: '#RMK' a: '@line-comment'  g: 'elem,comment' }
  { s: '#OP'  p: rav b: 1 u: { rav: true } g: 'elem,rav' }
]
rule: element: close: [
  { s: '#ELEM' r: element b: 1 g: 'elem,next' }   # another element
  { s: '#EEND' b: 1 g: 'elem,end' }               # hand back up
]

s is the token that selects the alternative, a an action, p a rule to descend into, r one to become, b how many tokens to give back. That is most of the vocabulary. Because it is data, you can print it, diff it, generate it — or hand it to an agent to write.

One table, two languages

The grammar lives in a single file. The build embeds the same compiled JSON into the TypeScript package and the Go module, so the two implementations cannot drift apart in the one place where drift would be hardest to spot.

TypeScript

import { parseGame } from '@tabnas/chess'

const game = parseGame('1. e4 e5 *')
game.moves[0].san    // 'e4'
game.moves[0].piece  // 'P'

Go

import chess "github.com/tabnas/chess/go"

db, _ := chess.Parse("1. e4 e5 *")
db[0].Moves[0].San    // "e4"
db[0].Moves[0].Piece  // "P"

They are held to it. A shared fixture set of tab-separated cases is run by both suites and compared against the same expected JSON — 351 assertions on the TypeScript side, the identical corpus on the Go side. A change that moves one runtime and not the other fails before it lands.

What comes back is plain data

No classes, no cycles, nothing to unwrap. Every field is something the notation actually said — and nothing that it did not. The parser has no board, so it will not tell you which knight played Nf3; it records the piece and the destination, because that is what was written. Resolving that is the component's job, with a legal move generator tested against published perft counts. 

parseGame('1. e4 {Best by test.} e5 (1... c5) 1-0')

{
  tags: {},
  moves: [
    { san: 'e4', piece: 'P', to: 'e4', number: 1, side: 'w',
      comments: [ { kind: 'brace', text: 'Best by test.' } ] },
    { san: 'e5', piece: 'P', to: 'e5', number: 1, side: 'b',
      variations: [ { moves: [ { san: 'c5', piece: 'P', to: 'c5', … } ] } ] }
  ],
  result: '1-0'
}

The error messages belong to the grammar

An engine that knows nothing about chess can only report that a character matched no active rule. A grammar can do better, because it knows what the language is made of — so the messages you saw above are set by the grammar, not the engine: 

error: {
  unexpected:           'not chess notation: {src}',
  unterminated_comment: 'this comment is never closed',
  unprintable:          'a tag value cannot contain a line break',
}

The diagram is generated from the grammar

Because the rule table is data, a tool can read it back. This railroad diagram was not drawn — @tabnas/railroad rendered it from the same grammar the parser is running.
